# Запуск и подготовка к размещению

Версия этапа 8 проверяется локально. Сайт не опубликован. Согласованный режим — **TEST, без списания денег**. Подключение реального провайдера, его sandbox и возвраты не входят в эту поставку.

## Локальный запуск Windows

Нужны Node.js >=22.12, npm и PostgreSQL. Проверенная среда: Node.js 24.20, PostgreSQL 17.11, Next.js 16.3.8. Из папки проекта:

```powershell
npm ci
if (!(Test-Path -LiteralPath .env)) { Copy-Item .env.example .env }
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/start-local-db.ps1
npm run db:migrate
npm run db:seed
npm run build
npm start
```

Существующий `.env` сохраняйте. Portable-скрипт подходит только для локальной разработки; он не заменяет настройку серверной PostgreSQL. `npm ci` генерирует Prisma-клиент автоматически. Seed не запускается автоматически и запрещён при `APP_ENV=production` или `NODE_ENV=production`.

Открыть: `http://127.0.0.1:3000`. Для редактирования кода вместо build/start: `npm run dev`. После изменения переменных перезапустите сервер. `.env`, `.local`, дампы и пароли не добавляйте в Git.

Для первого владельца:

```powershell
npm run admin:create -- --email owner@example.com --name "Владелец"
```

Команда скрыто запросит пароль дважды; существующий аккаунт не перезаписывается. Затем `/admin/login`. В основной базе QA владелец не создаётся.

## Согласованный тестовый режим

В отдельной демонстрационной базе `SalonSettings.isDemo=true`. Серверные переменные:

```dotenv
APP_ENV=demo
PAYMENT_MODE=TEST
PAYMENT_WEBHOOK_SECRET=<свой случайный секрет минимум 32 байта>
```

Секрет создайте локально и сохраните только в защищённой конфигурации. При слабом секрете адаптер отключён. Если платежи `DISABLED`, отключите требование предоплаты в настройках владельца, иначе бронь будет создана, но оплатить её нельзя. `deployment:check` выявляет такое сочетание.

```powershell
npm run deployment:check -- --local
npm run deployment:check
```

Первый вариант допускает отсутствие владельца с предупреждением для локального клиентского QA. Второй требует активного владельца. Оба читают каталог, режим оплаты, применённые/незавершённые миграции и SQL-защиту пересечений, ничего не меняют и не печатают секреты. Проверка не заменяет проверку TLS и резервных копий на сервере.

`APP_ENV=demo` оставляет административную cookie без Secure для локального HTTP. Если понадобится удалённое демо, закройте его внешней авторизацией/VPN и используйте HTTPS. Не принимайте настоящие контакты и деньги в этом режиме. Изолированный QA аккаунт с известным паролем предназначен только для loopback; QA-сервер нельзя публиковать.

## Сервер Node.js и PostgreSQL

Приложению нужен постоянный процесс Node.js: `next start`, PostgreSQL и обратный HTTPS-прокси. Статический HTML-хостинг не выполняет API и транзакции. Этот вариант не требует Docker для приложения. Имеющийся `docker-compose.yml` запускает только локальную базу; он не является комплектом production-развёртывания.

На выделенном сервере создайте отдельного пользователя приложения, отдельную БД и резервное копирование. Установите совместимый Node.js и зависимости из lock-файла. Строка `DATABASE_URL` хранится в защищённом окружении; PostgreSQL доступна только приложению/администраторам. Для сетевой БД настройте проверяемый TLS с доверенным сертификатом. Не отключайте проверку сертификата для обхода ошибки подключения.

У роли миграций должны быть права создания схемы, таблиц и расширения `btree_gist` либо расширение должен заранее установить администратор PostgreSQL. Runtime-роль не должна быть суперпользователем; нужны чтение/изменение таблиц, последовательности и транзакционные блокировки. Миграции применяет роль с необходимыми DDL-правами, после чего сервер использует runtime-подключение. `schema` в `DATABASE_URL` выбирает одну схему для Prisma и raw SQL; значение должно быть обычным PostgreSQL-идентификатором.

Процесс запуска на сервере, **после отдельной подготовки конфигурации и БД**:

```sh
npm ci
npm run db:validate
npm run db:migrate
npm run build
npm run deployment:check
npm start
```

Не запускайте `db:seed` на рабочей базе. Для demo с нуля выполните seed отдельным действием в demo-окружении до запуска. Для настоящего салона необходимы собственные сведения, каталог, назначения, графики и согласованные документы. Демонстрационный импорт не является их заменой. На этом этапе такие данные не подготовлены.

В настоящий production устанавливают `APP_ENV=production`, `PAYMENT_MODE=DISABLED`. TEST здесь запрещён. Пока реального адаптера нет, production может работать только **без требования онлайн-предоплаты**, с настоящими данными салона. Переключение переменной не превращает демонстрационный каталог и условия в реальные: проверка отклоняет обнаруженные demo-данные. Настройку настоящего салона и подключение провайдера выполняют отдельной задачей.

`npm start` слушает только `127.0.0.1:3000`; внешний доступ идёт через прокси. В `deploy/romeo.service.example` подготовлен пример службы Linux. Проверьте пути, пользователя и путь Node на своём сервере; скопируйте и включите службу только при явном решении размещать сайт. Служба читает защищённый файл окружения `/etc/romeo/romeo.env` и перезапускает Node при ошибке. Для сохранения существующего поведения приложение требует server-side переменные, без префикса `NEXT_PUBLIC_` для секретов.

## HTTPS-прокси

`deploy/nginx.conf.example` — пример, который требует своего домена, сертификата и путей. Прокси должен:

- принимать только выбранный домен и перенаправлять HTTP на HTTPS;
- передавать `Host` исходного сайта и **перезаписывать** `X-Forwarded-Proto` своим `$scheme`;
- не кэшировать динамические страницы/API и ограничивать размер тела;
- закрывать прямой внешний доступ к порту Node и PostgreSQL.

На stage 8 локально проверена production-сборка с `APP_ENV=production`: запросы с HTTPS Origin, исходным Host и заголовком прокси проходят вход и изменения; cookie Secure. Прямой HTTP вход и чужой Origin отклоняются. Сам TLS, сертификаты, nginx и systemd на удалённом сервере ещё не запускались. После установки проверьте конфигурацию nginx, домен и сертификат, а затем браузерный вход/выход и создание записи через настоящий HTTPS URL.

Не переписывайте Origin в прокси и не разрешайте CORS для админки. CDN должен обходить кэш для `/admin`, `/appointment` и `/api`; не записывайте тела запросов, Authorization, Cookie и личные ссылки в логи. Клиентский токен записи находится в URL-фрагменте, а API получает его через Bearer.

## Жизненный цикл и мониторинг

При запуске Node встроенный worker освобождает истекшие брони сразу и затем каждые 30 секунд; браузер для этого не нужен. Для постоянно работающего `next start` отдельный worker необязателен. В среде, которая останавливает процессы между запросами, нужен постоянный `npm run holds:worker` или внешний планировщик `npm run holds:expire`. Их параметры подключения должны совпадать с приложением. Эти команды меняют настоящую настроенную БД, это не QA.

`GET /api/health` возвращает только `{"status":"ok"}` / HTTP 200, если удаётся прочитать настройки и каталог PostgreSQL; иначе `{"status":"unavailable"}` / HTTP 503. Ответ no-store, без версии, строк подключения, пользователей или количества записей. Проверяйте его через прокси и наблюдайте за повторяющимися ошибками worker. Health не подтверждает наличие владельца, рабочий график, платёжный провайдер или доставку уведомлений.

База, `.env` и каталог `public` с собственными файлами должны сохраняться независимо от обновления приложения. Не используйте `migrate reset`, `db push` или удаление тома для обновления. Перед миграциями создавайте защищённый backup PostgreSQL, проверяйте восстановление в отдельной БД и сохраняйте предыдущий код/lock. При несовместимой схеме возврат только старого кода недостаточен: понадобится согласованная стратегия миграции либо восстановление копии с учётом записей после backup. Клиентские документы, доступы и политика хранения данных готовятся для реального салона отдельно.

## Повторение проверок

```powershell
npm ci
npm run typecheck
npm run lint
npm test
npm run db:validate
npm run test:db
npm run test:schedule
npm run test:appointments
npm run test:payments
npm run test:admin
npm run build
npm run test:admin:http
npm run test:admin:http -- --production
npm audit --omit=dev --audit-level=moderate
```

Интеграционные проверки создают и удаляют свои QA схемы в базе разработки; не запускайте их на production-подключении. Браузерный TEST сценарий: `npm run test:admin:http -- --serve --test-payments`, адрес `http://127.0.0.1:3001`. После проверки в терминале этого процесса введите `stop`, чтобы удалить QA данные. Windows Ctrl+C может прервать очистку раньше finally. Не запускайте две HTTP проверки одновременно: обе используют порт 3001.

Полный `npm audit` на 8 октября 2026: 5 high в dev-цепочке ESLint Next → fast-glob → micromatch → braces. [GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm) пока не имеет опубликованной исправленной версии; `npm view braces version` возвращает 3.0.3. Production audit — 0. Линтер не обрабатывает веб-запросы; используйте его только на доверенном коде, проверяйте обновления перед размещением. `npm audit fix --force` предлагает откат Next-конфига линтера на 14.x, это не безопасное совместимое исправление для этого проекта.

Сводка фактического QA и оставшихся ограничений — в `PROGRESS.md`. Публикация, настройка настоящего домена, сертификата и рабочей инфраструктуры этим этапом не выполняются.
