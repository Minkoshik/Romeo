# База данных, каталог, расписание, записи и тестовые платежи

На этапе 1 подготовлены схема Prisma, начальная SQL-миграция и скрипт демонстрационного заполнения. На этапе 2 полный клиентский путь работал без подключения к PostgreSQL. На этапе 3 каталог и публичные настройки подключены к PostgreSQL, а `src/lib/demo-catalog.ts` остаётся источником демонстрационных данных для seed и автоматических тестов.

Локальный PostgreSQL подключён. Демонстрационное заполнение выполнено дважды на этапе 3. Этап 4 подключил календарь и время к графикам без повторного заполнения рабочей базы; этап 5 добавил сохранение клиентов, записей, снимков условий и надёжное истечение броней. Этап 6 добавляет проверенные тестовые события, платёжные попытки и их ключи идемпотентности. Применённые миграции и результаты проверок записаны в [PROGRESS.md](../PROGRESS.md).

Серверный слой каталога находится в `src/lib/catalog-repository.ts`; Prisma-клиент с PostgreSQL-адаптером — в `src/lib/db.ts`. Общие правила сочетаний находятся в `src/lib/catalog-rules.ts`. `GET /api/catalog` возвращает публичные настройки, активные категории, услуги, варианты и мастеров с отметкой `source: "database"`; демонстрационные строки сохраняют `isDemo`. Настройки `SalonSettings` проверяются общей схемой перед передачей в интерфейс.

`POST /api/catalog/selection` проверяет выбранные `variantIds` и `masterId` по актуальному каталогу. Идентификаторы строк базы — UUID; slug используется для читаемых фильтров категории, а не для идентификатора мастера или правил его занятости. Для каждого варианта нужна активная связь `MasterService` с выбранным мастером. Неактивные или архивированные сущности не попадают в доступный выбор. Индивидуальное значение мастера имеет приоритет над значением варианта; отсутствующее переопределение означает значение варианта. Цены и длительности клиента не являются источником данных. Для каждой услуги разрешён один выбранный вариант.

`GET /api/availability` и `POST /api/demo/quote` получают актуальный каталог, настройки, недельные графики, исключения и занятые интервалы через `src/lib/availability-repository.ts`. Данные читаются в транзакции `RepeatableRead`. Серверный расчёт находится в `src/lib/availability-engine.ts`, преобразование локального времени салона в UTC — в `src/lib/salon-time.ts`. Прежние фиктивные интервалы используются только в исторических автоматических тестах. Quote дополнительно проверяет контакты и выбранный свободный интервал; если он устарел, возвращается `409`. Клиенты, записи и платежи при этом не сохраняются.

`POST /api/appointments` отдельно повторяет проверки и атомарно сохраняет `Customer`, `Appointment` и `AppointmentItem`. При ненулевой требуемой предоплате создаётся `WAITING_PAYMENT` со сроком в минутах из настроек базы (`HOLD_DURATION_MINUTES` задаёт только начальное значение seed). Эта бронь действительно резервирует интервал. При нулевой предоплате создаётся `CONFIRMED` без платежа. Тестовый адаптер этапа 6 создаёт `Payment` для собственной брони и подтверждает запись только после проверки серверного события. Прежняя симуляция этапа 2 остаётся в исторических тестах.

При недоступной или пустой базе встроенный демонстрационный каталог не используется как запасной источник. Seed сохраняет настройки и политику из окружения в `SalonSettings`; после загрузки каталога они используются интерфейсом и серверным расчётом, а тексты условий — страницами `/terms` и `/privacy`. Значения окружения задают предварительную оболочку до загрузки или при недоступной базе. Изменение `.env` само по себе не обновляет строку настроек; редактирование через админку относится к этапу 7.

## Совместимость и запуск

- Prisma ORM, CLI и PostgreSQL-адаптер закреплены на **7.10.0**. Версия 8 в момент подготовки была release candidate, поэтому не использована.
- В текущем Windows-окружении используется portable PostgreSQL **17.11-5** из официального архива EDB с проверкой опубликованного SHA-256. Бинарные файлы — `.local/postgres`, данные — `.local/postgres-data`; порт выбирается начиная с 5433, адрес доступен только на `127.0.0.1`. Итоговые результаты запуска фиксируются в `PROGRESS.md`.
- Локальная конфигурация Docker использует PostgreSQL 17. Порт доступен только на `127.0.0.1`; данные сохраняются в именованном томе.
- Для Docker задайте `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` и соответствующий `DATABASE_URL`. Не используйте демонстрационный пароль в рабочем окружении. `POSTGRES_PORT` необязателен, по умолчанию 5432; если меняете его, измените также порт в `DATABASE_URL`. Параметры подключения должны соответствовать выбранному экземпляру PostgreSQL.

Для portable варианта:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/start-local-db.ps1
npm run db:generate
npm run db:migrate
npm run db:seed
```

Первый запуск скачивает архив, проверяет SHA-256, создаёт локальный кластер и отдельную роль приложения без прав суперпользователя. Скрипт генерирует случайные пароли, сохраняет параметры подключения в `.env` и ограничивает права локальных файлов текущим Windows-пользователем и SYSTEM. Уже заданное пользовательское подключение не заменяется; разрешена автоматическая замена только демонстрационного подключения из `.env.example`. При повторном запуске используются существующие данные и сохранённый порт. `.local` и `.env` исключены из Git.

Остановка сохраняет кластер:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/stop-local-db.ps1
```

Пароли и строка подключения в документацию не записываются. Не переносите `.local` между проектами и не запускайте скрипт для чужого кластера; наличие существующего кластера без метаданных вызывает отказ вместо переинициализации.

Для Docker после настройки окружения:

```powershell
docker compose up -d
npm run db:generate
npm run db:migrate
npm run db:seed
```

Миграции требуют право создать расширение `btree_gist`. В управляемом PostgreSQL его может понадобиться заранее включить через администратора базы. `db:migrate` применяет подготовленные миграции; не заменяйте их командой `prisma db push`, поскольку она не создаёт ручные SQL-ограничения.

| Миграция | Изменение |
| --- | --- |
| `20261006000000_initial_foundation` | Начальная схема, ограничения денег, настроек, недельных интервалов и пересечения активных записей |
| `20261006020000_salon_buffer_policy` | Технический перерыв салона и разрешённая нулевая настройка предоплаты |
| `20261007030000_appointment_snapshots` | Отпечаток запроса, снимки телефона салона, страны и текстов условий; нулевая предоплата в снимке без вымышленного платежа |
| `20261007040000_demo_booking_terms` | Замена только известных прежних демонстрационных условий на описание сохранения настоящих записей; пользовательские тексты и снимки сохранённых записей не меняются |

`npm run db:validate` и `npm run db:generate` доступны без `DATABASE_URL`. Они сами по себе не подтверждают применение миграций к реальному PostgreSQL. В текущем локальном экземпляре четыре миграции применены; каталог, расписание, записи и ограничения дополнительно проверены интеграционно.

## Интеграционная проверка

После миграций локальной базы:

```powershell
npm run test:db
npm run test:schedule
npm run test:appointments
```

Проверка требует `DATABASE_URL`, существующие `public` и расширение `btree_gist`, а также права на создание собственной схемы. Все миграции, заполнение и изменения тестовых данных выполняются в новой схеме со случайным именем `qa_romeo_*`. Скрипт не принимает имя рабочей схемы для удаления; созданная им временная схема удаляется при завершении, включая завершение с ошибкой. Рабочие данные каталога не изменяются. Проверка запрещена при `NODE_ENV=production`.

`test:db` проверяет 30 групп: повторяемость seed, активные/архивированные сущности, назначения конкретных вариантов, индивидуальные цены и длительности, подмену итогов клиента, ошибки каталога, проверки денег и настроек в SQL, пересечение недельных интервалов и сохранение старых вариантов без удаления истории.

`test:schedule` проверяет 29 интеграционных групп: изменения недельных графиков непосредственно в базе, произвольного нового мастера, все виды исключений, обед и блокировки, всю длительность набора и индивидуальные перерывы, подтверждённые записи, действующие и истёкшие брони, смежные границы, интервалы из предыдущего дня, неактивные варианты, ошибки конфигурации, отсутствие приватных данных и отказ в устаревшем quote. Тестовые записи создаются только в собственной временной схеме и удаляются вместе с ней; рабочие записи не добавляются.

`test:appointments` проверяет 19 групп: суммы и UTC, шесть конкурентных заявок на один слот, пересечение с другим началом, буфер и точное касание границ, шесть повторов одного запроса, отказ при изменении запроса или токена, единый клиент для нормализованного телефона, устаревшие условия, полные тексты по 20 000 символов, откат при конфликте, действующий hold, истечение без браузера, освобождение просроченного hold перед созданием новой записи, нулевую предоплату, чужой доступ и неизменность снимков после изменения или архивирования каталога. Все три интеграционных набора пройдены; результаты последних общих и браузерных проверок находятся в [PROGRESS.md](../PROGRESS.md).

## Модель

| Сущности | Назначение |
| --- | --- |
| `SalonSettings` | Одна строка `salon`: контакты, RUB, часовой пояс, ограничения записи, предоплата и демонстрационные условия |
| `ServiceCategory`, `Service`, `ServiceVariant` | Каталог; цена, длительность и технический перерыв находятся у варианта услуги |
| `Master`, `MasterService` | Мастера и назначенные им варианты услуг; индивидуальные переопределения цены, длительности и перерыва |
| `WeeklySchedule` | Рабочие интервалы по дням недели, включая несколько интервалов за день |
| `ScheduleException`, `ScheduleExceptionInterval` | Изменение конкретного дня и несколько рабочих/заблокированных интервалов |
| `Customer` | Нормализованный телефон, контакты и приватные заметки администратора |
| `Appointment`, `AppointmentItem` | Состояние записи, занятый интервал, ключ повторного запроса и снимки условий |
| `Payment` | Отдельное состояние платежа и возврата, провайдер, режим TEST/LIVE и ситуации для проверки администратором |
| `PaymentEvent` | Уникальное проверенное событие провайдера, его отпечаток и результат обработки |
| `PaymentRequest` | Уникальный ключ запроса оплаты, привязанный к исходной попытке, включая ключи одновременных запросов |
| `AdminUser`, `AuditLog` | Будущая серверная авторизация и журнал действий; никаких общедоступных паролей |

Даже услуга с одной ценой имеет один внутренний вариант. В демонстрационном каталоге женская стрижка имеет одну цену 2 800 ₽ / 60 минут без выбора длины волос. Мастер назначается варианту; отсутствие активного назначения делает сочетание недоступным.

Деньги — целые минимальные единицы валюты: `220000` означает `2 200 ₽`. Процент предоплаты — базисные пункты: `2500` означает 25%. Требуемая предоплата рассчитывается сервером, ограничена полной стоимостью и сохраняется в снимке записи. Внесённая сумма считается по успешным платежам за вычетом подтверждённых возвратов; наличие требуемой суммы не означает оплату. TEST — только результат симуляции, без банковского списания.

Моменты создания, начала/конца записи и оплаты используют `timestamptz(3)`. Недельные рабочие интервалы используют локальные минуты от полуночи (0–1440); воскресенье — 0, понедельник — 1. `ScheduleException.localDate` — календарная дата салона типа `date`. Сервер преобразует её и минуты с учётом `SalonSettings.timezone`, независимо от часового пояса устройства клиента. Неоднозначные или отсутствующие часы при переходе на летнее/зимнее время не предлагаются.

Соединения PrismaPg задают `timezone=UTC`; транзакции дополнительно используют `SET LOCAL TIME ZONE 'UTC'`. Это обеспечивает правильное кодирование и чтение `timestamptz` независимо от часового пояса кластера PostgreSQL. Преобразование рабочего времени салона остаётся отдельным расчётом. Срок hold и `serverNow` берутся через `clock_timestamp()` в базе, а не из часов браузера.

При `CLOSED_DAY` день закрыт. При `REPLACE_DAY` интервалы `WORKING` полностью заменяют недельный график, затем вычитаются интервалы `BLOCKED`. При `BLOCKS_ONLY` блокировки вычитаются из обычного графика. Согласованность вида исключения с его интервалами проверяется сервером; некорректные данные закрывают доступность с безопасной ошибкой. Пустой график или замена без рабочих интервалов не предлагают свободного времени.

Длительность визита — сумма эффективных длительностей выбранных вариантов. Перерыв после всего визита — сумма эффективных `ServiceVariant.bufferMinutes` (с `MasterService.bufferMinutesOverride`) плюс `SalonSettings.bufferMinutes`. Индивидуальный ноль имеет приоритет над базовым значением. Весь интервал процедуры вместе с этим перерывом должен поместиться в один непрерывный рабочий интервал. Сетка начала задаётся `slotStepMinutes` от начала рабочих интервалов; блокировки не сдвигают сетку. Минимальное время до записи и горизонт берутся из настроек базы.

Занятость читается только для `CONFIRMED` и `WAITING_PAYMENT` с `holdExpiresAt > now`: используются `startsAt` и `occupiedUntil`. Отменённые, завершённые, пропущенные и истёкшие записи расчёту не мешают. Контакты, заметки, идентификаторы записей, платежи и приватные причины исключений не выбираются и не попадают в публичный API. Ответы имеют `no-store`; ошибка базы даёт `503` без подстановки фиктивной доступности.

## История и защита интервалов

Категории, услуги, варианты и мастера имеют `archivedAt`. Связи с используемыми сущностями запрещают физическое удаление; позиции записи дополнительно сохраняют названия, цены, длительности и перерывы. Запись содержит снимки салона, мастера, контактов, валюты и политики предоплаты. Статусы записи и платежа разделены.

Ручная SQL-часть миграции задаёт проверки денег, интервалов и настроек. PostgreSQL-ограничение `Appointment_no_active_overlap` запрещает пересечение полуоткрытых интервалов `[startsAt, occupiedUntil)` одного мастера для статусов `WAITING_PAYMENT` и `CONFIRMED`. `occupiedUntil` включает технический перерыв. Завершение одного интервала ровно в момент начала следующего допустимо.

На этапе 5 сервер атомарно проверяет доступность и создаёт записи внутри `Serializable`. Порядок advisory-блокировок постоянный: ключ идемпотентности, затем мастер. После блокировки мастера его просроченные hold переводятся в `EXPIRED`, затем повторно читаются каталог и график и проверяется весь выбранный интервал. Сериализационные и уникальные гонки повторяются с новым снимком транзакции. SQL-конфликт интервала даёт `409`, а откат исключает незавершённого клиента или позиции услуг. Транзакции ограничивают ожидание блокировки и запроса; временная ошибка базы даёт безопасный `503`.

Клиент нормализуется по международному телефону, который уникален в `Customer`. Контакты каждого визита сохраняются отдельно снимком; изменение данных клиента или каталога не переписывает прежний визит. Снимки включают салон, его адрес и телефон, мастера, контактные данные, валюту, цены, длительности, перерывы, политику предоплаты и полные согласованные тексты. Хеши версий условий передаются при создании без отправки полных текстов обратно, поэтому запрос остаётся в лимите 16 KiB даже при длинных условиях.

`idempotencyKey` уникален. `requestFingerprint` — SHA-256 канонического нормализованного запроса. Повтор с тем же ключом, токеном и данными возвращает ту же запись с актуальным статусом; попытка заменить данные или секрет даёт `409`. Повтор переживает изменение цен, условий, имён и архивирование исходного каталога, поскольку возвращает сохранённый снимок. Перенос, отмена и другие административные изменения ещё не реализованы; на этапах 7.3–7.4 они должны брать ту же блокировку мастера.

## Истечение без браузера

`src/lib/appointment-expiry-worker.ts` выполняет `UPDATE` только строк `WAITING_PAYMENT` с `holdExpiresAt <= clock_timestamp()`, меняя статус на `EXPIRED` и сохраняя историю. В долгоживущем Node-сервере `src/instrumentation.ts` запускает обработчик немедленно и каждые 30 секунд. Во время сборки и в Edge runtime он не запускается. Singleton предотвращает дублирование таймера при HMR; новый tick не пересекается с текущим, временная ошибка PostgreSQL не останавливает следующие попытки. Логи содержат безопасные сообщения и количество освобождённых броней, без контактов, токенов или строки подключения.

Для постоянного отдельного процесса размещения:

```powershell
npm run holds:worker
```

Он держит процесс работающим и по `SIGINT`/`SIGTERM` ожидает текущую проверку с закрытием соединения; крайний срок завершения — 15 секунд. При короткоживущих серверных функциях используйте отдельный постоянный worker: встроенный таймер не гарантирует работу вне времени жизни процесса.

Однократная обработка текущей базы:

```powershell
npm run holds:expire
```

Это рабочие команды, а не изолированные тесты: они используют `DATABASE_URL` и изменяют статусы подходящих броней. Истечение также проверяется перед новым созданием у мастера и при приватном чтении самой записи. Доступность сразу исключает просроченные hold; статус для снятия SQL-ограничения обновляется обработчиком или внутри создания. После перезапуска накопившиеся hold истекают при первом tick. Семь автоматических тестов обработчика проверяют немедленный запуск, интервал, отсутствие перекрытия, остановку, восстановление после ошибки, HMR и безопасные логи; проверка восстановления выполнена и с настоящим отключением локальной базы.

## Личный доступ и тестовая оплата

Личная ссылка `/appointment/<UUID>#token=…` содержит случайный секрет из 32 байтов. Фрагмент не попадает в URL серверного запроса; клиент передаёт токен в `Authorization: Bearer …` для `GET /api/appointments/<UUID>`. В `publicAccessTokenHash` хранится только SHA-256; исходный токен и отпечаток запроса не возвращаются API. Ошибочный, отсутствующий или чужой токен и неверный UUID дают одинаковый `404`. Страница и API отключают кеширование и передачу referrer. Личная страница опрашивает статус сервера каждые 15 секунд; отсчёт опирается на серверное время и монотонные часы устройства. Сохранённая ссылка работает после перезагрузки без черновика формы; ссылка предоставляет доступ к контактному снимку.

При ненулевой требуемой предоплате hold не подтверждается до проверенного платёжного события. Внутренний `ROMEO_TEST` работает только при `APP_ENV=demo`, `PAYMENT_MODE=TEST`, сильном серверном `PAYMENT_WEBHOOK_SECRET` и `SalonSettings.isDemo=true`. Настоящий салон и `APP_ENV=production` блокируют создание, симуляцию и обработку тестовых платежей. Секрет не попадает в публичные настройки. Нулевая требуемая предоплата во всех трёх режимах подтверждает запись сразу без hold и платежа.

`POST /api/appointments/[id]/payments` принимает только ключ идемпотентности и приватный Bearer. Сумма и валюта берутся из снимка записи, идентификаторы сессии создаёт сервер. В один момент у записи может быть только один `PENDING`: частичный уникальный индекс защищает и прямой SQL. `PaymentRequest` сохраняет все принятые ключи, чтобы повтор ключа после ошибки воспроизводил ту же попытку. Новая попытка не продлевает исходный hold.

`POST /api/payments/events/test` проверяет HMAC-SHA256 **точных байтов** тела в `x-romeo-signature`, строгую схему и время события (±5 минут). Проверяются идентификаторы платежа, записи и провайдера, сумма и валюта. `PaymentEvent` уникален по провайдеру/режиму/eventId: одинаковый повтор не применяет оплату снова, изменение содержимого под тем же ID даёт конфликт. Сырое тело, токены и секрет подписи не сохраняются. Приватный `simulate` создаёт подписанное сервером событие и использует этот же обработчик; возвращение клиента на страницу недостаточно для подтверждения.

Обработка события проходит транзакционно с блокировкой мастера и защитой от пересечений. После истечения hold успешная оплата повторно проверяет исходный UTC-интервал, сохранённую длительность и буфер по текущему расписанию и занятости; ограничение minimum lead для новой записи не отменяет уже согласованный будущий визит. При конфликте сохраняется `SUCCEEDED` с `needsAttention`, а запись не занимает чужой интервал. Поздний успех может заменить ошибку/отмену/истечение платежа; последующая ошибка не отменяет успех. Дополнительный успешный платёж отмечается для проверки салоном. Возврат автоматически не выполняется и не имитируется. Реквизиты карт в таблицы не сохраняются.

Истечение броней и `PENDING`-сессий выполняется сервером независимо от браузера. Приватный просмотр возвращает отдельные статусы записи и платежей, рассчитанные `paidMinor` и `remainingMinor`, безопасный текст `needsAttention` без внутренних заметок. Настоящий внешний провайдер и официальный sandbox отложены по выбору пользователя; их проверка подписи и подтверждённые возвраты требуют отдельной интеграции.

Пароли администратора должны появиться только после отдельной безопасной процедуры этапа 7.1; seed администратора не создаёт. В `AuditLog.changes` сервер должен записывать только необходимые изменения и исключать пароли, токены и платёжные секреты.

## Демонстрационное заполнение

Seed содержит 6 категорий, 10 услуг с 12 активными вариантами и 3 мастера. Он сохраняет настройки и политику из `getSalon()` в `SalonSettings`, включая горизонт, минимальное время до записи, шаг интервалов, срок временной брони, технический перерыв, размер предоплаты и тексты условий. Процент переводится в базисные пункты: демонстрационные 25% сохраняются как `2500`.

Назначения `MasterService` сохраняют индивидуальные значения: мужская стрижка у Марка — `250000` минимальных единиц валюты / 75 минут. Пустое переопределение означает значение варианта. Старые демонстрационные варианты женской стрижки и их назначения архивируются с `isActive=false` и `archivedAt`, без удаления истории. Ручные строки с другими идентификаторами сохраняются.

Подготовленный демонстрационный график — понедельник–суббота, 10:00–14:00 и 15:00–20:00; воскресенье — выходной. Начиная с этапа 4 именно эти строки используются интерфейсом, без вымышленных занятых часов или отпуска из прежнего файла. Изменения графика или исключений отражаются после следующего серверного обновления. В текущей локальной базе seed выполнен дважды на этапе 3, итоговые количества строк сохранены без дублей; перезапуск PostgreSQL также сохранил данные.

Идентификаторы демонстрационных строк детерминированы; повторный запуск обновляет те же строки. Seed обновляет демонстрационные строки каталога и графика, поэтому запускайте его только в базе для разработки. Он запрещён при `NODE_ENV=production`, при валюте, отличной от RUB, и полностью прекращает заполнение, если настройки, категория, услуга или мастер отмечены как настоящие (`isDemo=false`). Отдельная проверка не позволяет переиспользовать идентификатор варианта или назначения для другой пары сущностей. Все изменения seed выполняются транзакцией. Он не удаляет историю и не создаёт клиентов, записи, платежи, администратора или вымышленные отзывы.

Изменение настоящих данных выполняется через будущую админку, а не повторным seed. Перед запуском салона замените демонстрационные настройки, цены, графики и тексты условий.
